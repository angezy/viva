# Weluxo website sitemap

This sitemap documents the routes currently present in the `fend` Next.js app and the `bend` Express/GraphQL backend. It separates public pages, functional/private pages, redirect aliases, frontend API routes, and backend endpoints.

## Route conventions

- Public site origin: configure `SITE_URL`/`STORE_URL` per deployment (use `http://localhost:3000` in local development).
- Backend origin: `http://localhost:5000` in local development.
- Browser API calls use the frontend origin and are proxied to the backend through `/api/[...path]` using `BACKEND_URL`.
- Dynamic segments use Next.js notation such as `[slug]`, `[categoryId]`, `[orderId]`, and `[ticketId]`.
- `/dashboard` and `/admin` require an authenticated admin session and redirect to `/signin/admin` otherwise.
- The route list below is based on the current `fend/.next/app-path-routes-manifest.json` and the source files under `fend/src/app`.
- `GET /sitemap.xml` and `GET /robots.txt` are generated by `fend/src/app/sitemap.js` and `fend/src/app/robots.js`.

## Catalog and category structure

Categories are now real customer-facing pages. `/shop` still supports search and trending products, while category links resolve to `/category/[categoryId]`.

Seed data currently includes:

- `Training`
- `Strength`
- `Recovery`

The dashboard product form accepts arbitrary category text, so the concrete indexable category URLs are determined by the categories returned from `/api/shop`.

| URL | Behavior | Status |
|---|---|---|
| `/shop` | Full catalog with search and add-to-cart actions | Implemented |
| `/category/[categoryId]` | Loads the catalog, filters by category slug, and renders a category grid | Implemented; dynamic |
| `/product/[slug]` | Loads the catalog, resolves a product slug, and renders product details | Implemented; dynamic |

Product detail data includes the product name, brand, category, price, stock, description, image gallery, fulfillment address where available, and same-category related products. The browser catalog endpoint is `GET /api/shop`; the legacy single-product endpoint is `GET /api/product/[productId]`.

## Cart and checkout

The checkout experience is now a multi-step flow. Checkout state is saved on the device while the customer moves between steps.

```text
/shop
  → Add to Cart
/cart
  → Review items and begin checkout
/checkout
  → Overview
/checkout/information
  → Email, phone, and marketing preference
/checkout/shipping
  → Shipping address and delivery method
/checkout/payment
  → Payment method and provider-ready payment confirmation
/checkout/success/[orderId]
  → Confirmation, delivery details, tracking, and invoice links
```

| URL | Page/state | Purpose | Status |
|---|---|---|---|
| `/cart` | Shopping cart | Items, quantities, removal, totals, and checkout action | Implemented; customer session required for cart API actions |
| `/checkout` | Checkout overview | Review customer, shipping, payment, and order summary state | Implemented |
| `/checkout/information` | Customer information | Collects email and contact phone | Implemented |
| `/checkout/shipping` | Shipping | Collects address and standard/express method | Implemented |
| `/checkout/payment` | Payment | Starts Stripe-hosted Checkout; the order is created only after the backend verifies a paid Stripe session | Implemented; requires server-side Stripe configuration |
| `/checkout/success/[orderId]` | Success | Shows confirmation, order summary, delivery details, tracking, and invoice links | Implemented; dynamic |
| `/checkout/failed/[orderId]` | Failed payment | Allows payment retry or return to cart | Implemented; dynamic |
| `/checkout/cancelled/[orderId]` | Cancelled checkout | Preserves the cart and offers checkout/cart/shop links | Implemented; dynamic |
| `/checkout/return` | Provider return | Handles success, canceled, and pending provider return query states | Implemented |
| `/checkout/cancel` | Legacy cancel alias | Redirects to `/checkout/cancelled/legacy` | Redirect |
| `/checkout/success` | Legacy success alias | Redirects to a dynamic success page when `orderId` is supplied, otherwise to `/order-confirmation` | Redirect |

The payment UI is provider-ready but does not collect raw card details. The backend payment endpoints are `POST /api/payment/create`, `POST /api/payment/confirm`, and `POST /api/orders/create`.

## GraphQL API

The backend also exposes:

- `http://localhost:5000/graphql`

The current schema defines these query operations:

```graphql
products: [Product]
product(ProductId: ID!): Product
categories: [Category]
category(CategoryId: ID!): Category
shopItems: [ShopItem]
homeContent: [HomeContent]
```

Current GraphQL types:

- `Product { ProductId, name, price }`
- `Category { CategoryId, name, products }`
- `ShopItem { id, name, price }`
- `HomeContent { id, message }`

There are no GraphQL mutations or subscriptions in the current schema.

## Follow-up status

1. Contact submission is implemented through `POST /api/support/tickets`; SendPulse notification delivery remains configuration-dependent.
2. Stripe-hosted Checkout is integrated behind `PAYMENT_PROVIDER=stripe`, `STRIPE_SECRET_KEY`, and `APP_BASE_URL`. Checkout fails closed when those values are not configured, and orders are only marked paid after Stripe verification.
3. Generated `GET /sitemap.xml` and `GET /robots.txt` routes are implemented. Private, admin, API, checkout, account, invoice, and support paths are excluded from crawling.
4. `/dashboard/tikects` remains the current compatibility route, with `/admin/tickets` aliases redirecting to it.
